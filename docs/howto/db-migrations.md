# Database migrations

How to change the schema of an app-owned SQL Server database (a new table,
column, index, stored proc, view, permission row, data backfill, etc.) and get
that change onto INT and PROD safely.

If you only want the 10-second version, jump to [TL;DR](#tldr).

## Mental model: two scripts, two roles

| Script | Direction | What it does |
|--------|-----------|--------------|
| `scripts/db-migrate.py` | **forward** | Runs ordered migration files against a DB and records each one in `dbo.SchemaMigrations`. This is what *changes* the schema. |
| `sql/sync-from-db.py` | **read-only** | Dumps the *current* INT schema into per-object `.sql` files under `sql/<Db>/` for review and code search. Never changes a database. |

The **live INT database is the source of truth** for committed-state DDL. The
per-object files under `sql/<Db>/Tables/`, `Views/`, `Programmability/`, etc.
are auto-generated by `sync-from-db.py` and **must never be hand-edited**. You
move the schema forward *only* by writing a migration; the per-object dump
just mirrors whatever resulted.

Migrations are **immutable once applied**. The runner stores a SHA-256 checksum
of each applied file; if you later edit a file that's already been applied, the
next run refuses with an error. To change something, write a *new* migration.

## What's tracked

Only the two app-owned databases have migrations:

| `sql/_migrations/` folder | `nx_lib.config` attr | Notes |
|---------------------------|----------------------|-------|
| `NexoraDB/`               | `DB_NEXORA`          | The app's own DB (users, permissions, config). |
| `GeneraliDB/`             | `DB_GENERALI`        | Tenant-specific Generali DB. |

`StatisticsDB` (sydoc_stat) and `OctoDB` are **deliberately excluded** — they're
treated as runtime/vendor surfaces, not schema we own. Don't add migrations for
them.

Both tracked DBs live on the same server (`DB_SERVER_PRD`) and authenticate with
`DB_UID` / `DB_PWD`, all read from `env/<ENV>.env`.

## Layout

```
sql/
  NexoraDB/            <- auto-generated per-object dump (DO NOT hand-edit)
    Tables/  Views/  Programmability/{StoredProcedures,Functions,Triggers,Types}  Security/{Users,Roles,Schemas}
  GeneraliDB/          <- same layout, auto-generated
  _migrations/         <- you write files HERE
    NexoraDB/
      0001_init_schema_migrations.sql   <- bootstrap, creates dbo.SchemaMigrations
      0002_....sql
    GeneraliDB/
      0001_init_schema_migrations.sql
  sync-from-db.py      <- read-only INT -> per-object dump
  requirements.txt     <- mssql-scripter
scripts/
  db-migrate.py        <- applies pending migrations
```

## One-time setup per clone

The normal path is `bootstrap.ps1`, which installs the dependencies and wires
the git hooks (via the [pre-commit framework](https://pre-commit.com/)) for you:

```powershell
.\bootstrap.ps1
```

If you're setting things up by hand instead, you need:

```powershell
# 1. mssql-scripter (used by sync-from-db.py)
pip install -r sql/requirements.txt

# 2. SQL Server Command Line Utilities — provides sqlcmd, used by db-migrate.py.
#    Ships with SSMS / the mssql-tools package. Confirm it's reachable:
sqlcmd -?

# 3. Git hooks (pre-commit framework — installed into .venv by bootstrap/uv sync)
pre-commit install --install-hooks
pre-commit install --hook-type commit-msg
pre-commit install --hook-type pre-push
```

`pyodbc` (already a runtime dependency) is used by the runner for the
`SchemaMigrations` bookkeeping; `sqlcmd` runs the actual DDL batches.

## The standard workflow

### 1. Write the migration file

Create `sql/_migrations/<Db>/NNNN_short_description.sql`, using the **next**
4-digit number for that DB. A file may contain one or more SQL batches separated
by `GO`.

```sql
-- sql/_migrations/NexoraDB/0007_add_user_theme_column.sql
IF NOT EXISTS (
    SELECT 1 FROM sys.columns
    WHERE object_id = OBJECT_ID('dbo.Users') AND name = 'ThemePreference'
)
BEGIN
    ALTER TABLE dbo.Users ADD ThemePreference NVARCHAR(20) NOT NULL
        CONSTRAINT DF_Users_ThemePreference DEFAULT 'system';
END
GO
```

**Make migrations idempotent** with `IF NOT EXISTS` / `IF EXISTS` guards (as
above). Idempotent migrations survive being re-applied by the pre-commit hook
without any special handling. This matters because of how the hook applies
pending files — see step 3.

### 2. Apply it to INT

Two ways:

**a) Let the runner apply it** (preferred — the runner is also what runs on
PROD, so you exercise the same path):

```powershell
python scripts/db-migrate.py --env INT
```

**b) You already ran the statements in SSMS while prototyping.** Record them as
applied so the hook doesn't try to run them again:

```powershell
python scripts/db-migrate.py --env INT --mark-applied
```

> `--mark-applied` records the file's checksum in `dbo.SchemaMigrations` **without
> executing it**. Use it only when the DDL is already live on INT. (Idempotent
> migrations don't strictly need this — they'll no-op on re-apply — but it keeps
> the bookkeeping honest.)

Preview without touching anything:

```powershell
python scripts/db-migrate.py --env INT --dry-run
```

### 3. Commit — the hook does the rest

On `git commit`, the **pre-commit** stage runs two local hooks
(see `.pre-commit-config.yaml`):

1. `sql-migrate-int` → `python scripts/db-migrate.py --env INT`
   **auto-applies** any pending migrations to INT.
2. `sql-sync-check` → `python sql/sync-from-db.py --check`
   re-dumps the per-object DDL from INT and **fails if it drifted** from what's
   committed.

If either fails, the commit is **blocked**. Common cases:

- A SQL error in your migration → fix the file and re-commit.
- Drift detected → the regenerated `sql/<Db>/...` files are left unstaged;
  review them, `git add sql/`, and re-commit.
- You ran the DDL manually in SSMS but didn't `--mark-applied` first, and it's
  **not** idempotent → the hook's apply step errors trying to re-create an
  existing object. Run `--mark-applied` (step 2b), then re-commit.

Offline / no DB access? Bypass both checks:

```powershell
$env:SQL_SYNC_SKIP = "1"; git commit -m "..."   # then: Remove-Item Env:\SQL_SYNC_SKIP
# or
git commit --no-verify
```

(Don't leave `SQL_SYNC_SKIP` set in your shell — unset it after the commit.)

### 4. Push to main → PROD gets it automatically

When the change lands on `main`, the deploy workflow
(`.github/workflows/deploy.yml`) runs **`python scripts/db-migrate.py --env PROD
--yes`** as a dedicated step, **before** it stops the IIS app pool. So:

- Migration succeeds → deploy proceeds, code is mirrored, app pool restarts on
  the new schema.
- Migration **fails** → the deploy **aborts** and the running app keeps serving
  the old code on the old schema. Nothing breaks; you fix the migration and push
  again.

For an **ad-hoc PROD migration** from your dev box (e.g. a hotfix outside the
deploy pipeline):

```powershell
python scripts/db-migrate.py --env PROD          # one [y/N] confirm per DB
```

## `db-migrate.py` flag reference

```
python scripts/db-migrate.py [options]

--env INT|PROD        Which env/<ENV>.env to load (default: INT).
--db NexoraDB|GeneraliDB
                      Limit to a single DB folder (default: all tracked DBs).
--dry-run             Show what's pending; don't run anything.
--check               Exit 1 if any migrations are pending (used by pre-commit).
                      Doesn't apply anything.
--mark-applied        Record pending files as applied WITHOUT running them
                      (when you already ran them in SSMS).
--yes / -y            Skip the per-DB PROD confirmation prompt (used by deploy).
```

Environment escape hatch: `SQL_SYNC_SKIP=1` makes the script exit 0 immediately
without contacting any database (also disables the pre-commit check).

## `dbo.SchemaMigrations` — the ledger

Each tracked DB has a `dbo.SchemaMigrations` table (created by the bootstrap
migration `0001_init_schema_migrations.sql`). The runner reads and writes it:

| Column      | Meaning |
|-------------|---------|
| `FileName`  | Migration filename (primary key) — recorded once applied. |
| `AppliedAt` | UTC timestamp (`SYSUTCDATETIME()`). |
| `AppliedBy` | SQL login that applied it (`SUSER_SNAME()`). |
| `Checksum`  | `BINARY(32)` — SHA-256 of the file's bytes at apply time. |

A migration is considered "applied" when its `FileName` is present. On every
run the script also compares the on-disk checksum against the recorded one — if
they differ, the file was edited after being applied, which is always a mistake.
The run fails (exit code 3) and tells you to add a new migration instead. This
is the immutability guarantee.

To inspect what's been applied:

```sql
SELECT FileName, AppliedAt, AppliedBy
FROM dbo.SchemaMigrations
ORDER BY FileName;
```

## `sync-from-db.py` — keeping per-object DDL in sync

This is the read-only side. It runs `mssql-scripter` against INT, producing one
`.sql` per object, then organizes the flat output into the SSMS-style folder
tree under `sql/<Db>/`.

```powershell
python sql/sync-from-db.py                 # sync all tracked DBs from INT
python sql/sync-from-db.py --db NexoraDB   # one DB
python sql/sync-from-db.py --check         # pre-commit mode: exit 1 on drift
python sql/sync-from-db.py --env PROD      # rare: dump from PROD instead of INT
```

You rarely run this by hand — the pre-commit `sql-sync-check` hook runs
`--check` for you and surfaces drift. When you *do* run it manually (e.g. after
someone changed INT outside a migration), review the regenerated files, then
`git add sql/` and commit them alongside the migration that explains the change.

## Recipes

**A new index, idempotently:**

```sql
-- sql/_migrations/NexoraDB/00NN_index_workitems_status.sql
IF NOT EXISTS (
    SELECT 1 FROM sys.indexes
    WHERE name = 'IX_WorkItems_Status' AND object_id = OBJECT_ID('dbo.WorkItems')
)
    CREATE INDEX IX_WorkItems_Status ON dbo.WorkItems (Status);
GO
```

**A new/updated stored procedure** (use `CREATE OR ALTER`, which is naturally
re-runnable):

```sql
-- sql/_migrations/NexoraDB/00NN_update_spGetUserPermissions.sql
CREATE OR ALTER PROCEDURE dbo.spGetUserPermissions
    @UserId INT
AS
BEGIN
    SET NOCOUNT ON;
    -- ...
END
GO
```

**A new permission row** (data, not schema — still goes through a migration):

```sql
-- sql/_migrations/NexoraDB/00NN_add_perm_generali_pdqm_export.sql
IF NOT EXISTS (SELECT 1 FROM dbo.Permissions WHERE Code = 'generali.pdqm.export')
    INSERT INTO dbo.Permissions (Code, Description)
    VALUES ('generali.pdqm.export', 'Export PDQM data');
GO
```

## Troubleshooting

| Symptom | Cause / fix |
|---------|-------------|
| `sqlcmd not found on PATH or in common install dirs` | Install SQL Server Command Line Utilities (ships with SSMS / mssql-tools). The runner also probes well-known install dirs; if you just installed it, restart the shell. |
| `mssql-scripter not found` | `pip install -r sql/requirements.txt`. |
| Commit blocked: `N migration(s) edited after being applied` | You changed a file that's already in `dbo.SchemaMigrations`. Revert the edit and add a *new* migration instead — migrations are immutable. |
| Commit blocked: `sql/ drifted from INT` | INT changed without (or beyond) what your migration captured. Run `python sql/sync-from-db.py`, review, `git add sql/`, re-commit. |
| Hook tries to re-apply a migration I ran in SSMS and errors | It wasn't recorded. `python scripts/db-migrate.py --env INT --mark-applied`, then re-commit. (Or make the migration idempotent with `IF NOT EXISTS` guards.) |
| `Missing DB_SERVER_PRD / DB_UID / DB_PWD in env` | `env/<ENV>.env` isn't populated. See `env/<ENV>.env.example`. |
| Need to commit with no DB connectivity | `SQL_SYNC_SKIP=1 git commit ...` or `git commit --no-verify`. Apply the migration to INT later before pushing. |

## TL;DR

```powershell
# 1. write sql/_migrations/<Db>/NNNN_desc.sql (next number, GO-separated, idempotent)
# 2. apply to INT
python scripts/db-migrate.py --env INT
#    (or, if already run in SSMS:)  python scripts/db-migrate.py --env INT --mark-applied
# 3. commit — pre-commit hook re-applies to INT + verifies the per-object dump
git add sql/_migrations/<Db>/NNNN_desc.sql sql/<Db>/
git commit -m "feat(db): ..."
# 4. push to main — deploy.yml applies pending migrations to PROD before the app pool stops
```
