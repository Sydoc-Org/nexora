# Security audit — unauthorized-access review (issue #193)

**Date:** 2026-08-10 · **Branch audited:** `v3.1` · **Method:** 9 parallel attack-surface lenses read the live code, each finding adversarially confirmed/refuted against the source by an independent verifier, then deduped and ranked. 19 raw findings → 16 after merge, **0 refuted**.

> This document is a map of exploitable weaknesses. It lives under `docs/security/` which is **excluded from the deploy mirror and from Confluence publishing** on purpose — keep it that way. Do not paste finding detail into the public issue tracker beyond what the owner chooses to disclose.

## Executive summary

Session auth is sound where it is applied — bcrypt + TOTP 2FA + CSRF + hardened cookies. The weakness is **authorization**: nexora checks coarse permission *codes* thoroughly but frequently skips *per-object / per-tenant* entitlement, so the multi-tenant boundary the compound `(client, id)` identity was built to protect leaks in the workitem detail path.

Overall posture: **weak** (fixable — the gaps are concentrated, not systemic).

**Close these three first, in order:**

1. **Cross-tenant workitem IDOR (rank 1, high).** Any user with the flat `workitems.details.view*` codes reads *another* tenant's document fields, page images and audit trail by setting `?client=` and iterating small integer ids. Live on the PROD surface today.
2. **Passwordless dev-login backdoor (rank 2, high).** `/dev/login/<username>` + `/dev/users` = become any user (incl. admin) with no password/2FA, gated only on `ENVIRONMENT != PROD`. Inert on the PROD box today, but a full auth bypass the instant any INT/STAGING/TEST instance is network-reachable.
3. **Generali cross-org read (rank 3, high).** A user holding only `*.edit.organizational` reads *every* organization's records by omitting or spoofing the `?organizationcode` query param — the self-restriction only triggers when the caller has *neither* edit grant.

Everything below the top three is low/info defense-in-depth.

## Cross-cutting themes

- **Object-level authorization is missing where permission-code checks pass.** The app verifies you hold `workitems.details.view*` / `generali.*.view` but never that the *specific* workitem/org you asked for is yours. The `(client, id)` boundary is enforced in the list/export path (`client_process_pairs`) but not the by-id detail path; the same shape recurs in Generali list routes and the external API's `ClientCode`.
- **The "not PROD = trusted" fallacy.** Security-critical controls are gated on `IS_PROD` — the dev-login backdoor, *all* Talisman headers + secure-cookie flags, and the dev_login open redirect. With a documented public ngrok tunnel and real INT/STAGING/TEST deployments, "non-PROD" ≠ "unreachable"; these controls silently vanish on any exposed non-PROD worker.
- **Boundaries deferred to out-of-band convention instead of enforced in code.** The reporting SQL sandbox's cross-DB isolation rests entirely on RO-login DBA grants with no schema/catalog allowlist; the API's per-client scope is a property of `ProcessName` strings on an unconstrained `StatConfig`; external-API auth relies on every future author remembering `@require_api_key`. Each is safe today but has no code-level backstop.
- **Defense-in-depth erosion that amplifies other bugs.** The CSP ships `'unsafe-inline'` (zero XSS mitigation), which upgrades the `fullname |safe` sink from theoretical to executable; rate limits are per-worker in-memory with no account lockout; raw exception strings leak schema hints.

## Detailed findings

### 1. Cross-tenant IDOR — workitem detail / page-image / audit endpoints — **high**

**Surface:** `/api/get_media_info`, `/api/get_media_raw`, `/api/get_audithistory`
**Files:** `nx_lib/views/workitems.py` (1717, 1827, 1929), `nx_lib/octo.py`, `nx_lib/workitem_sources.py`

The three by-id detail endpoints resolve which tenant's runtime to query from an entirely caller-controlled `?client=` value and fetch an arbitrary workitem id, gated **only** by the flat detail-view permission — never by whether the caller is entitled to that workitem's client/process. `api_get_media_info` checks only `has_permission('workitems.details.view')`, reads the client via `_client_hint()` (validated only as a *known* client code — `hint in CLIENTS`, `workitems.py:459-460`), then `get_workitemdata_param` fetches the document, extracted field values and source locations with no ownership filter. `api_get_media_raw` streams raw page images; `get_audithistory` returns the full audit trail — same pattern.

The per-process entitlement model (`client_process_pairs`) is built and consulted **only** in the list/export path (`workitems.py:542, 827`); it appears nowhere in the three detail endpoints, and there is no `@before_request` ownership guard *(independently confirmed: grep shows `client_process_pairs` only at 542/827)*. Route type is `<int:workitem_id>` and ids are small sequential integers, so enumeration is trivial. Sensitive-field stripping (`strip_sensitive_from_detail`) still applies, so *sensitive* doc-fields stay protected — but non-sensitive extracted fields, full page images, and the audit trail are disclosed unconstrained.

**Attack:** a user granted only `workitems.details.view.images` for one default-client process issues `GET /api/get_media_raw/1216/0?client=ms02` (and the `_info` / `_audithistory` variants), iterating `workitem_id` over the small integer space — scriptable cross-tenant document exfiltration.

**Fix:** add a shared `assert_entitled_to_workitem(workitem_id, client)` called at the top of all three endpoints: (1) validate `?client=` against the caller's granted client set instead of trusting it; (2) resolve the requested workitem's owning `(client, process)` and confirm it is in the caller's `client_process_pairs` allow-list before fetching; 403/404 otherwise.

### 2. Passwordless dev-login backdoor — **high** *(merged: F0, F5, F16, F7)*

**Surface:** `/dev/login/<username>`, `/dev/users`
**Files:** `nx_lib/views/auth.py` (491-522, 525-536, 881-882), `nx_lib/hooks.py:38-50`, `nx_lib/config.py:75`

`dev_login(username)` establishes a fully-authenticated session for **any** username with no password, no bcrypt, no TOTP and no CSRF — it looks the user up by name, `session.clear()`, sets `session['userid'/'username'/'permissions'/org]`, loads real permissions, records an active session, and redirects to their start page. `dev_users()` dumps every username as JSON to feed it. Both are registered **unconditionally** and the only guard is `if IS_PROD: abort(404)` where `IS_PROD = os.environ.get('ENVIRONMENT') == 'PROD'` — so on INT/STAGING/TEST both are fully live. Both paths are in `_SESSION_ENFORCE_SKIP_PATHS`, so no session/permission middleware touches them. No loopback / `remote_addr` check.

The documented ngrok tunnel runs on SYAPP01 (the PROD box) where these routes 404 — so **not internet-reachable today** — but it becomes a full remote auth bypass + privesc the moment any non-PROD instance is network-reachable (VPN pivot, ad-hoc tunnel, LAN, misconfig). Folded in (F7): the `next=` redirect at `auth.py:518-520` only checks `startswith('/')` not `startswith('//')`, so `//evil.com` passes as a scheme-relative open redirect — moot once the route is removed.

**Fix:** do not register `/dev/login` and `/dev/users` in any server-reachable environment. Gate registration behind an explicit opt-in flag (e.g. `NEXORA_DEV_LOGIN=1` set only by the local `nx` CLI) **and** require `request.remote_addr in ('127.0.0.1','::1')` — never gate a credential-free login on the negation of `IS_PROD`.

### 3. Generali cross-org read via unclamped `?organizationcode` — **high**

**Surface:** `nx_lib/views/generali.py` — reporting / attendance / baseservices / projectmanagement / pdqm list + month-report endpoints
**Files:** `nx_lib/views/generali.py`

Generali distinguishes `*.edit.organizational` (own org only) from `*.edit.transorganizational` (all orgs). Writes enforce it correctly (`_check_generali_record_org`, session-org comparison at 1422/1916/2405/2968) and the dropdown/month-report helpers derive org from the session. The list/read endpoints do **not**. In `api_generali_reporting_list`, `restrict_to_self` is True **only** when the caller has *neither* edit grant (739-741), so a user holding just `*.edit.organizational` skips the restriction. The only org filter is `org_code = request.args.get('organizationcode')` (709), taken straight from the query string, never compared to `session['organizationcode']`, with no session-org fallback. Omitting `organizationcode` leaves the WHERE clause with no user/org predicate → the entire `dbo.reportingiss` table for all orgs (with per-user names joined); passing a rival `org_code` returns that org. The identical pattern repeats in the other four families (restrict at 1286/1689/2183/2727; client org_code at 1267/1764/2257/2806).

**Attack:** a sub-org team lead with `generali.reporting.edit.organizational` + `.view` calls the API directly (the UI only offers their own org): `GET /api/generali/reporting/list` (no `organizationcode`) → every org's records; `?organizationcode=<rival>` → that rival's. Same across all five families.

**Fix:** for callers lacking `*.transorganizational`, always constrain the query to the session's own org server-side — ignore/override any client-supplied `organizationcode` and inject `_generali_userids_in_org(session['organizationcode'])` (or reject when requested ≠ session org). Apply to all five list routes + the month-report endpoints.

### 4. Reporting SQL sandbox — no DB/schema allowlist — **low** *(split-issue)*

**Files:** `nx_lib/reporting/sandbox.py`, `nx_lib/views/reporting.py`, `nx_lib/db.py`, `scripts/provision-reporting-ro-logins.sql`

`validate_select()` validates only statement *shape* (single statement, read-only root, no DML/DDL nodes, keyword blocklist) and places **no** restriction on which databases/schemas/objects a SELECT targets. `SELECT * FROM NexoraDB.dbo.Users`, `SELECT name FROM sys.databases`, or a four-part linked-server name all parse as an ordinary `exp.Table` and pass — `_BLOCKED_WORDS` lists only `OPENROWSET/OPENQUERY/OPENDATASOURCE`, not four-part names. The connection string pins `DATABASE=` but that is only the default catalog, not an access boundary. So the **entire** boundary is the server-side RO-login grant. The provisioning script maps each login as `db_datareader` in exactly one DB and creates no user in NexoraDB/GeneraliDB, so with guest disabled those DBs are unreachable **today** — but this is out-of-band DBA convention with no code-level backstop. Separately, `reporting.sql.target.octopus` already grants raw SELECT over the whole Octo runtime DB irrespective of per-client `reporting.scope.process.*` grants.

**Fix:** add an object-scope check to `validate_select()` — walk the AST for `exp.Table` nodes and reject any carrying a catalog/db qualifier (cross-DB / four-part) or referencing `sys` / `INFORMATION_SCHEMA` / `master`. Defense-in-depth: confirm the RO logins are DENIED CONNECT / guest in every other DB and hold no linked-server mappings.

### 5. External API `ClientCode` boundary never enforced — **low** *(fix-now)*

**Files:** `nx_lib/views/api_external.py`, `nx_lib/api_auth.py`, `nx_lib/views/dashboard.py`, `sql/NexoraDB/Tables/dbo.StatConfig.sql`, `sql/_migrations/NexoraDB/0038_create_api_keys.sql`

`require_api_key` stores `g.api_client['client_code']` but no `/api/v1` route reads it. `api_v1_stats_today` forwards only the key's `ProcessList` to `compute_today_stats`, which selects `FROM Statconfig WHERE ProcessName IN (...)` with **no** `ClientCode` predicate — `ClientCode` is fetched only to route default-vs-ms02 legs, not to filter tenant. `dbo.StatConfig` has no PK/UNIQUE and `ProcessName` is NULLable. If any single `ProcessName` exists under two `ClientCode`s (plausible config drift — this repo has a documented history of missing-unique-constraint dup-key bugs on sibling config tables), a key issued for tenant A silently sums tenant B's rows. Not client-controllable (the client can't alter its own `ProcessList`), so this is a config-dependent cross-tenant leak, not a self-service attack. `api_v1_backlog` is stronger — it reconstructs `(client, process)` pairs.

**Fix:** enforce the key's `ClientCode` server-side — add `AND ClientCode = ?` (bound to `g.api_client['client_code']`) to the `Statconfig` lookup, or pre-filter `target_processes` by matching `ClientCode`. Add a UNIQUE constraint on `StatConfig(ProcessName, ClientCode)` and validate `ProcessList` entries against the key's `ClientCode` at issuance.

### 6. No session-ID rotation on auth / privilege change — **low** *(needs-owner-decision)*

**Files:** `nx_lib/views/auth.py` (343-355, 401-413, 508-522), `nx_lib/__init__.py:33-42`

Every login-completion path calls `session.clear()` and repopulates the dict but never regenerates the server-side session identifier. Under the PROD Flask-Session filesystem backend the SID is derived from the inbound signed cookie and reused across the pre-auth → authenticated transition — no session fixation defense. `SESSION_USE_SIGNER` means an attacker can't *forge* a SID, and the PROD cookie is Secure + HttpOnly + SameSite=Lax, which closes the easy injection/MITM vectors — hence low. A valid signed SID planted in a victim's browser (cookie-injection sibling host, intermediate proxy, XSS) would become authenticated once the victim logs in.

**Fix:** mint a fresh SID (not only `session.clear()`) at successful authentication and on privilege change.

### 7. No per-account lockout; per-worker in-memory rate limits — **low** *(split-issue)*

**Files:** `nx_lib/views/auth.py` (539, 370-416), `nx_lib/extensions.py:20-23`

`login()` is capped at `10/min` and `verify_2fa`/`init_2fa` at `30/hour`, but flask_limiter uses the default in-memory backend which under wfastcgi is **per-worker** (the TODO at `extensions.py:20-23` says so) — effective ceiling = limit × N_workers. The limiter keys on `get_remote_address`, and there is **no** per-account failure counter or lockout anywhere: a wrong password/TOTP just re-renders with an error and never increments a durable per-user counter. TOTP's key space (`valid_window=1`) keeps 2FA guessing impractical, but a distributed multi-IP password-spray against a known account faces only per-worker per-IP throttling with no account-level backstop.

**Fix:** back flask_limiter with shared storage (NexoraDB/Redis) so limits are global, and add a durable per-account failed-attempt counter with temporary lockout / step-up on both stages.

### 8. Username enumeration via login timing oracle — **low** *(fix-now)*

**Files:** `nx_lib/views/auth.py:553-588`

`login()` fetches the user row first and calls the expensive `bcrypt.checkpw()` only inside `if user_record:`. A non-existent username returns the identical 401 without ever paying the bcrypt cost, so response latency (tens–hundreds of ms, well above network jitter) distinguishes valid from invalid usernames. `request_password_reset()` was deliberately hardened against exactly this oracle; `login()` was left with the gap. Rate limit + 2FA keep real-world impact to information disclosure; matters mostly on PROD where `/dev/users` 404s.

**Fix:** always perform a bcrypt comparison against a fixed dummy hash when the user row is missing, so both branches spend equivalent time (constant-time login).

### 9. Stored/self XSS via `fullname |safe` — **low** *(fix-now)*

**Files:** `templates/dashboard.html:29`, `nx_lib/views/profile.py:57`, `nx_lib/views/admin.py` (767, 861)

`dashboard.html:29` renders the name via `"<strong>"|safe ~ fullname ~ "</strong>"|safe)|safe` — the whole expression is `|safe`, so `fullname` is **not** escaped. `profile.py:57` reads `request.form['fullName']` with no sanitization and writes it verbatim to `Users.fullname` **and** `session['fullname']`, so it renders on the very next `/dashboard` without re-login; admin create/edit store `fullname` verbatim. Because the CSP allows `'unsafe-inline'` (finding 10), an injected `<img src=x onerror=…>` / `<svg onload=…>` executes. Kept low: `connect-src 'self'` blunts fetch-exfil, self-XSS is low value, and the admin→other-user path needs `admin.create.user`.

**Fix:** don't wrap the whole `gettext` result in `|safe` — render the name through normal autoescaping (`Markup()` only around the literal `<strong></strong>`, escaped value inside). Independently validate/limit `fullname` on write.

### 10. CSP allows `'unsafe-inline'` — **low** *(needs-owner-decision)*

**Files:** `nx_lib/config.py:193-206`

The Talisman CSP hard-codes `'unsafe-inline'` in both `script-src` and `style-src` with no nonce or hash. With `'unsafe-inline'` in `script-src` the browser executes any inline `<script>` and inline event-handler attribute, so the CSP contributes **zero** defense against HTML/script injection. It also whitelists three third-party CDNs in `script-src`. Standalone this grants no access, but it directly upgrades the `fullname |safe` sink (finding 9) from theoretical to executable.

**Fix:** remove `'unsafe-inline'` from `script-src` and adopt a per-response nonce (`content_security_policy_nonce_in=['script-src']`), attaching the nonce to the app's own `<script>` tags. Drop CDN script sources not actually used. *(Owner call: this touches every inline script in the templates — non-trivial migration.)*

### 11. Security headers + secure cookies gated on `IS_PROD` — **low** *(fix-now)*

**Files:** `nx_lib/__init__.py:33-48`, `nx_lib/config.py:75`

Talisman (CSP, HSTS, X-Frame-Options, X-Content-Type-Options, referrer policy) is installed only under `if cfg.IS_PROD`. Session-cookie hardening (Secure/HttpOnly/SameSite, USE_SIGNER, filesystem backend, lifetime) is likewise only applied inside `if cfg.IS_PROD:`. So any instance not started with `ENVIRONMENT=PROD` serves with no CSP, no HSTS, no X-Frame-Options (clickjacking), no X-Content-Type-Options, and a session cookie **without** Secure/HttpOnly/SameSite (transmittable over plaintext HTTP, readable by JS). Same "non-PROD is not unreachable" concern as the dev-login backdoor.

**Fix:** apply Talisman and the secure-cookie config unconditionally (tune `force_https` per environment), or at minimum set `SESSION_COOKIE_HTTPONLY`, `SAMESITE` and X-Frame-Options in every environment. Never expose a non-PROD instance through a public tunnel.

### 12. Raw exception strings returned to clients — **low** *(fix-now)*

**Files:** `nx_lib/views/generali.py:228` (~45 sites), `nx_lib/views/admin.py:289` (~20 sites), `nx_lib/views/dashboard.py:348`, `nx_lib/views/reporting.py:1141`

Many handlers return the raw exception message to the client, e.g. `jsonify({'success': False, 'error': str(e)}), 500`. The top-level 500 handler renders a clean template with no traceback, but these per-route catches bypass it and can surface pyodbc/SQL Server driver messages, SQL fragments and internal identifiers — reconnaissance that aids schema/injection probing. Defense-in-depth only (authenticated, schema hints not data/credentials).

**Fix:** return a generic error to the client and log `str(e)` via `current_app.logger` server-side only. Reserve verbose SQL error text for the reporting SQL sandbox where it is an intended feature over RO logins.

### 13. No `MAX_CONTENT_LENGTH` → upload memory-exhaustion DoS — **low** *(fix-now)*

**Files:** `nx_lib/__init__.py:21-82`, `nx_lib/views/profile.py:100-115`, `nx_lib/views/workitems.py:1685-1691`

No `MAX_CONTENT_LENGTH` / `MAX_FORM_MEMORY_SIZE` is set anywhere. Several upload paths buffer the entire request body into memory: the profile avatar handler does `io.BytesIO(); f.save(...)` then reads it fully, and the MS02 prepared-audit import does `file.stream.read()` then hands the bytes to openpyxl. A single request can pin arbitrary worker memory. Authenticated DoS, not an access-control break.

**Fix:** set `app.config['MAX_CONTENT_LENGTH']` (a few MB, sized to the largest legitimate PID xlsx / avatar) in `create_app` so Werkzeug rejects oversized bodies before buffering; prefer streaming the xlsx to a temp file with a size guard.

### 14. xlsx MIME allowlist defeats content sniffing — **low** *(fix-now)*

**Files:** `nx_lib/files.py:16-34`, `nx_lib/views/workitems.py:1685-1691`, `nx_lib/workitem_sources.py:527`

`is_file_allowed()` maps `.xlsx` to `{openxml-spreadsheet, application/zip, application/octet-stream}`. Since `application/octet-stream` is libmagic's generic-binary fallback and `application/zip` matches any container, the sniff collapses to an extension check for anything named `*.xlsx`; any zip/arbitrary binary renamed `.xlsx` passes and is fed to `openpyxl.load_workbook`. Combined with the absent size cap (finding 13) this removes the sniff as a defense against a decompression-bomb xlsx. DoS-only, gated by `workitems.import.preparedaudit` on an MS02 deployment.

**Fix:** drop `application/octet-stream` from the xlsx allowlist (keep zip + the OOXML type), enforce `MAX_CONTENT_LENGTH`, and guard the openpyxl load against decompression bombs.

### 15. External-API auth is per-route convention on an exempt path — **info** *(fix-now)*

**Files:** `nx_lib/views/api_external.py`, `nx_lib/hooks.py`, `nx_lib/api_auth.py`

Authentication on `/api/v1` is applied per-view via `@require_api_key` rather than by a blueprint-wide `before_request` guard, while `/api/v1` and `/api/test/v1` are carved out of the normal session/CSRF/HTML error handling. All four current routes are correctly decorated — no live bypass — but the surface's safety rests on every future author remembering the decorator; a new `/api/v1/*` route added without it would be reachable with **no** authentication at all.

**Fix:** move auth to a `before_request`-level guard keyed on the `/api/v1` path prefix (fail-closed unless a view explicitly opts out), **or** add a test asserting every url_rule under `/api/v1` (minus a documented allowlist) is wrapped by `require_api_key`.

### 16. Legacy unencrypted `{SQL Server}` ODBC driver — **info** *(needs-owner-decision)*

**Files:** `nx_lib/db.py:20-48`

`get_db_url` / `get_ro_db_url` build the ODBC string with `DRIVER={SQL Server}` and no `Encrypt=yes` / `TrustServerCertificate`. The legacy driver does not negotiate TLS by default, so app↔SQL Server traffic — including the UID/PWD login handshake and all row data — can travel unencrypted on the internal network. The MS02 Postgres engines by contrast enforce `sslmode=require`. Internal-network exposure (defense-in-depth), not internet-reachable.

**Fix:** move to ODBC Driver 17/18 for SQL Server with `Encrypt=yes` (valid cert / `TrustServerCertificate=no`), consistent with the TLS already enforced on the Postgres engines.
